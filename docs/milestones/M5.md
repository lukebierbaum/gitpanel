# M5 — Merge conflict resolver

**Goal:** PyCharm's *Merge Revisions* dialog in the terminal: ours | result | theirs, per-chunk accept, edit, then mark resolved — reached from the Commit window's *Merge Conflicts* group or the operation banner, for merges, rebases, cherry-picks and reverts alike.

## Backend — `git/conflicts.py`
| Function | Behaviour |
|---|---|
| `conflicts(git) -> list[Conflict]` | unmerged paths with their code (`UU`, `AA`, `DU`, `UD`, `AU`, `UA`, `DD`) and which stages exist |
| `stages(git, path) -> Stages(base, ours, theirs)` | text of `:1`/`:2`/`:3` (None when absent), binary flag |
| `merge_model(stages) -> MergeModel` | runs `git merge-file -p --diff3` on temp copies and parses it into `Common(lines)` / `Chunk(ours, base, theirs)` segments; non-conflicting changes are already merged in `Common` |
| `MergeModel.result()` | text with each chunk's resolution (`ours`, `theirs`, `ours+theirs`, `theirs+ours`, custom lines); unresolved chunks keep conflict markers |
| `resolve_with(git, path, text)` | write the file and `git add` it |
| `accept(git, paths, side)` | whole-file ours/theirs, handling delete/modify (`git rm` when the chosen side deleted it) |
| `ours_label / theirs_label` | "ours = main", "theirs = feature" from MERGE_HEAD / rebase `onto` / CHERRY_PICK_HEAD so the panes are named the way PyCharm does (rebase swaps them) |

## Actions (`actions/builtin/conflicts.py`)
| id | key | where |
|---|---|---|
| `conflict.resolve` | `enter` | Commit window, conflict file → opens the resolver |
| `conflict.accept_ours` / `conflict.accept_theirs` | `alt+left` / `alt+right` | conflict files (whole file) |
| `resolver.take_ours` / `take_theirs` | `left` / `right` | resolver, current chunk |
| `resolver.take_both` / `take_both_reversed` | `b` / `B` | resolver |
| `resolver.edit` | `e` | resolver, edit current chunk in a text dialog |
| `resolver.reset` | `u` | resolver |
| `resolver.apply` | `ctrl+s` | write result + `git add`; asks if chunks remain unresolved |
| `resolver.next` / `prev` | `n` / `p` | resolver navigation (view keys) |

## UI
- `screens/resolver.py` — full-screen `ResolverScreen` (has `context()`): header with file, labels and unresolved count; `ThreeWayView` (Line API) with aligned ours | result | theirs columns, the current chunk highlighted, unresolved chunks shown as markers in the result column.
- Commit window: `enter` on a conflict opens the resolver; the diff pane shows a conflict summary instead of the "arrives in M5" note.

## Acceptance tests
1. `merge_model` of a two-chunk conflict: resolutions produce the expected text; non-conflicting edits from both sides are kept.
2. `accept` ours/theirs for content and delete/modify conflicts; `resolve_with` stages the file and the banner's conflict count drops.
3. Labels for merge vs rebase (sides swapped) vs cherry-pick.
4. Actions via FakeUi: take ours on chunk 1, theirs on chunk 2, apply → file content and index correct; merge then continues.
5. Pilot: conflict → `enter` → `left`, `n`, `right`, `ctrl+s` → file resolved, banner says ready to continue.

## As built
- The resolver is a full `Screen` exposing `context()`; per-chunk actions operate on the `MergeModel` published in `ctx.form["merge"]` / `["chunk"]` and post `resolver.changed` so the view re-renders and jumps to the next unresolved chunk.
- Common regions show the auto-merged text in all three columns (dimmed); conflicting chunks show the real ours / result / theirs lines side by side.
- Binary and delete/modify conflicts skip the resolver and point to Accept Yours / Accept Theirs (`alt+←` / `alt+→`), which handle `git rm` for the deleting side.
