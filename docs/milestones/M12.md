# M12 — Stacked pull requests

**Goal:** see every stack in the repository, build stacks, restack them and merge them from the PR window. GitHub now has stacked PRs (a `PullRequestStack` per stack, created and merged with the official `gh stack` extension, `github/gh-stack`); gitpanel shows those, and also shows chains that *aren't* GitHub stacks yet — clearly labelled — with one key to turn them into one.

## Why inside gitpanel
A stack is branches plus PRs. GitHub (via `gh stack`) owns the PR side: the stack object, linking, and the atomic stack merge. The branch side — rebasing every layer onto its new base, conflicts, undo — is git, and gitpanel already has the pieces: scripted rebase, the resolver and banner, the journal, `--force-with-lease` push, the PR window.

## Decisions
1. **Chains that aren't GitHub stacks are shown as stacks**, with a clear label: PRs whose bases chain (`#13` based on `#12`'s branch) and local branches built on each other (no PRs yet) both show as stacks marked **`not a GitHub stack yet`**, with an action to make them one.
2. **After a restack, ask** before pushing (`[prs] restack_push = "ask"`).
3. **Merging uses GitHub's atomic stack merge** (`gh stack merge`): merging a PR in a stack merges it *and everything below it* in one all-or-nothing step. Merge on the **top** PR merges the whole stack; on a **middle** PR it merges up to that PR and asks whether to merge the whole stack instead; on the **bottom** PR it asks too (whole stack, or just this PR).
4. **All stacks in the repository** are shown, not only ones with your PRs — there's a *Stacks* list for exactly that.

## Kinds of stack
| Kind | How it's found | Label in the UI | Make it a GitHub stack |
|---|---|---|---|
| **GitHub stack** | `PullRequest.stack` (GraphQL) is set; order from `stackEntry.position` | `Stack #7` (GitHub's stack number) | — |
| **Chained PRs** | open, same-repo PRs where one's `baseRefName` is another's `headRefName`, not in a GitHub stack | `not a GitHub stack yet` | `L` → `gh stack link 12 13 14` |
| **Local chain** | unmerged local branches where one branch's nearest ancestor among them is another (see Backend); branches may or may not have PRs | `local · not a GitHub stack yet` | `L` → `gh stack link b1 b2 b3 --base main` (pushes, creates the missing PRs with chained bases, links them) |

Forks can't be parents (a PR's base must be a branch of the base repository), so cross-repo PRs only sit at the top of a stack.

## Phases
| Phase | Scope | Size |
|---|---|---|
| **12a — See stacks** | stack data from GitHub + chain detection; stacks grouped in the PR list; *Stacks* list; stack strip in Overview with jump keys | ≈ M3 |
| **12b — Build stacks** | `L` link / publish as a GitHub stack; `n` suggests the stacked base; `N` new branch on top; new PRs join their parent's stack | ≈ M3 |
| **12c — Restack** | rebase the whole stack onto its new base in one go (one undo step), conflicts through the normal resolver, ask, push all branches | ≈ M5 |
| **12d — Merge** | stack-aware `M`: atomic merge of a PR and everything below; whole-stack prompts as in Decision 3 | ≈ M3 |

### 12a — See stacks
- **Data.** The batched status query (`GitHub.statuses`) also asks for `stack { number size baseRefName } stackEntry { position }`, so every listed PR knows its GitHub stack at no extra request. The *Stacks* list and chain detection use a cheap list of all open PRs (`number,headRefName,baseRefName,headRefOid,isCrossRepository,author,title,isDraft`, limit 300, cached like the other lists).
- **PR list.** With `[prs] stack_view` on and no column sort active, each stack is kept together: a dim group line (`Stack #7 · 3 PRs · main` or `⚠ not a GitHub stack yet · 3 PRs · main — L to link`), then its PRs bottom-up with `├`/`└` and a dim `2/3`. Sorting by a column (`>` / header click) shows the plain list; going past the last column returns to stack order. Needs two generic `ListTable` additions: *group rows* (non-selectable label rows between items) and a *context hook* that runs after filtering and may add items back — used to keep a match's whole stack visible.
- **Stacks list** (new entry in the query dropdown, Decision 4): every stack in the repository — GitHub stacks, chained PRs, and your local chains — grouped as above. Local-chain branches without a PR appear as rows `branch-name  no PR yet` (a second item type in the list: `StackItem = PullRequest | LocalLayer`).
- **Overview strip** above the description: `Stack #7  main ← #12 ✓ Approved ← #13 ● (this) ← #14 ✗ Changes`, each in its CI/review colour, or the `not a GitHub stack yet` label. `[` / `]` jump to the PR below / above (loading it if it's outside the current list). Members come from `stack { entries(first: 50) { nodes { position pullRequest { … } } } }` for GitHub stacks, from the chain otherwise.
- **Commits / Files** need no change: they diff against `merge-base(base, head)`, and the base is the parent's branch, so each PR shows only its own layer.

### 12b — Build stacks
- **`L` — Make GitHub Stack.** On a chained-PR stack: confirm, then `gh stack link <bottom> … <top>`. On a local chain: confirm listing what happens (push N branches, create M PRs as drafts unless you pick *ready*, link them), then `gh stack link <branches…> --base <trunk> [--open]`. Afterwards the list refreshes and the stack shows as `Stack #N`.
- **`n` (create PR)** from a branch: candidates are open-PR head branches `H ≠ B` with `merge-base --is-ancestor H B`; the nearest (fewest commits in `H..B`) becomes the default base. If that parent is in GitHub stack `#N`, the form has *Add to Stack #N* (on by default) → after `gh pr create`, `gh stack link N <new pr>` (the stack-number shortcut appends to the top).
- **`N` — New Branch on Top** (on a PR or a local-chain branch): name prompt, branch from that head, checked out (Smart / Force Checkout as for `enter`). It shows up as part of the local chain right away; `n` creates its PR later (`gh` refuses empty PRs).
- Requires the `gh stack` extension (`gh extension list` contains `github/gh-stack`). Without it, `L` and stacked merges explain how to install it (`gh extension install github/gh-stack`); seeing stacks needs only `gh`.

### 12c — Restack
**When:** a lower PR merged, or a lower layer got new commits (review fixes), so the layers above no longer sit on it. Such stacks are marked `⟲ needs restack` (a parent's head isn't an ancestor of its child, or the bottom's base moved past what the bottom contains).

**gitpanel does the rebase itself**, not `gh stack rebase`: conflicts then go through gitpanel's resolver and banner, and the whole restack is one undo step. `gh stack rebase` would stop mid-stack and expect `gh stack rebase --continue`, which the banner and journal don't know about. The result is what `gh stack rebase` produces (each layer has the previous layer's tip in its history, same branch names), so `gh stack` keeps working on the stack afterwards.

**What it does,** for the stack containing the selected PR, in one `journal.mutation("Restack Stack #7")`:
1. Fetch the stack's branches and the base (one `git fetch`).
2. Build one todo, bottom to top: each layer's own commits as `pick`s, then `update-ref refs/heads/<layer>`. A layer's own commits are `<old parent head>..<layer head>`.
3. Check out the top branch and run `scripted_rebase.run(session, new_base, todo)` (rule 7). Git moves every intermediate branch when it finishes.
4. Conflicts stop as usual: *Rebase in progress (3/7)*, the resolver opens, Continue finishes — the `update-ref`s survive restarts.
5. **Ask** (Decision 2), listing each branch old → new head; then one `git push --atomic --force-with-lease=<b>:<expected>` (expected = the remote-tracking sha before the restack, so someone else's push makes it fail instead of being overwritten).
6. Bases: GitHub stacks keep their chaining; for chained PRs whose parent merged without deleting its branch, `gh pr edit <n> --base <new base>`.

**Squash-merged parents.** A squash merge puts one new commit on `main` whose patch-id matches none of the parent's commits, so patch-id detection can't tell which of the child's commits are already in. The reliable boundary is the parent's **final head sha** — the child's own commits are exactly `<parent head>..<child head>`. Source, in order: the merged PR's `headRefOid` (still returned after merging and branch deletion); `refs/gitpanel/pr/<n>`; the shared stack file (below). Only without any of these fall back to `git log --cherry-pick --right-only <new base>...<child>`, and say so in the confirmation.

**Refusals:** a layer checked out in another worktree (offer to switch there); an operation in progress; local branches behind their remote (offer to fast-forward first).

**Undo** restores every branch of the stack in one step. Pushes and base changes are remote and aren't undone — the confirmation says so.

### 12d — Merge
`M` on a PR in a stack becomes stack-aware (Decision 3). It always uses GitHub's atomic stack merge — `gh stack merge <pr> --yes --merge-method <m>` merges that PR and everything below it, all or nothing:

| Where the PR is | Choices (first = default) |
|---|---|
| **top** | Merge the whole stack #12–#14 |
| **middle** (#13) | Merge #12–#13 (this PR and everything below) · Merge the whole stack #12–#14 |
| **bottom** (#12) | Merge the whole stack #12–#14 · Merge #12 only |
| not in a stack | the existing M11 merge dialog |

- The form keeps the method (`[prs] merge_method`) and lists every PR being merged with its CI / review state; warnings (draft, failing checks, changes requested, conflicts) cover all of them. Branch protection is evaluated by GitHub when the merge runs; a failure merges nothing and is reported. With a merge queue the stack is queued.
- **Chained PRs (not a GitHub stack yet):** the dialog first offers *Link as a GitHub stack and merge* (link, then the atomic merge) or *Merge this PR only* (the plain M11 merge).
- After a partial merge, the PRs above stay stacked on the new base; if they need it, the result offers a restack (12c).
- Auto-merge isn't available for stacks (`gh stack merge` has no `--auto`).

## Backend
| Module | Contents |
|---|---|
| `forge/models.py` | `StackInfo(number: int \| None, position: int, size: int, base: str)` on `PullRequest` (filled by `statuses()` / `pr()`); `Stack(kind: "github" \| "chain" \| "local", number: int \| None, base: str, layers: tuple[Layer, ...])` with `position(pr)`, `below(pr)`, `above(pr)`, `needs_restack`; `LocalLayer(branch, head_sha)` |
| `forge/github.py` | stack fields in `statuses()` and `pr()`; `stack_members(number)`; `open_pr_index()` (cheap list of all open PRs); `stacks(index, statuses, local_chains) -> list[Stack]` (pure); `has_stack_extension()`; `stack_link(items: Sequence[str], base: str \| None, ready: bool)` → `gh stack link`; `stack_merge(pr, method)` → `gh stack merge <pr> --yes --merge-method`; `retarget(n, base)` → `gh pr edit <n> --base` |
| `git/stack.py` (new, no forge import) | `local_chains(git, trunk) -> list[list[str]]` (unmerged local branches; parent = nearest other candidate that is an ancestor, by fewest commits between); `nearest_base(git, branch, candidates) -> str \| None`; `restack_todo(git, layers)`; `async def restack(session, new_base, layers) -> RebaseResult` (checks out the top branch, calls `scripted_rebase.run`); a small shared file `<common-dir>/gitpanel/stacks.json` recording each layer's parent head at create / restack time (rule 10) — the squash-merge boundary of last resort |
| `git/remote.py` | `push_many(git, remote, branches, leases, *, atomic=True)` |
| `actions/builtin/prs.py` | the actions below; maps PRs / branches to `Layer`s and calls `git/stack.py` |

`git/stack.py` takes plain branch names and shas, so the git layer stays free of `forge` (rule 1); the actions join the two.

Keys checked against the PR window: `enter w o y n r m M c R x` taken, `<` `>` sort, `/` filter. Hints show `[ ] stack`, `L link` / `S restack` when they apply.

## Config
```toml
[prs]
stack_view = true          # keep stacks together in the PR list (off: plain list)
restack_push = "ask"       # ask | always | never — push the branches after a restack
```

## Testing
- **Fake gh:** stack fields in the GraphQL status / detail queries; `gh extension list`; `gh stack link` (creates or extends a stack, creates PRs for branches without one, chains bases) and `gh stack merge <pr> --yes --merge-method m` (merges that PR and everything below atomically; refuses everything if one can't merge); `gh pr edit <n> --base`.
- **Backend (real git):** chain detection incl. a cross-repo PR that can't be a parent; `local_chains` on branches with and without PRs; `nearest_base`; a 3-layer restack after a **squash merge** of the bottom — each branch ends up with only its own commits; after **new commits on a middle layer**; a **conflict mid-stack** → resolve → Continue → all three branches moved; **undo** restores all three refs in one step; `push_many` lease rejection.
- **Actions (FakeUi):** merge choices for top / middle / bottom / unstacked PRs and the commands they run; link vs. publish confirmations; missing-extension message; restack refusal for a layer checked out in another worktree; push asked after restack.
- **Pilot:** grouped stack rows with their labels, the *Stacks* list, filter keeps the whole stack, `[` / `]`, `⟲ needs restack`.

## Out of scope (for now)
- Reordering, splitting or folding layers (`gh stack modify` covers it; gitpanel could later drive it through the interactive rebase editor).
- Other stacking tools' metadata (Graphite, ghstack, spr, git-town, jj) — their PRs show up as chained PRs and can be linked with `L`.
- Auto-merge for stacks (not offered by `gh stack merge`).
