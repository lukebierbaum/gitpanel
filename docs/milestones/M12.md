# M12 — Stacked pull requests

**Goal:** see, create, restack and merge stacks of pull requests (PR #13 based on #12's branch, #14 on #13's …) from the PR window, with one undo step per restack. Native git and `gh` only — no extra tool to install.

## Why inside gitpanel
The GitHub web UI shows stacked PRs as unrelated PRs with odd bases, and after the bottom one merges it leaves the rest to you. What's missing is a *git* operation: rebase each layer onto its new base, move every branch, push them. gitpanel already has the pieces — scripted rebase, the conflict resolver and banner, the journal, `--force-with-lease` push, the PR window — so a stack is mostly a new view over them.

## Phases
| Phase | Scope | Size |
|---|---|---|
| **12a — See the stack** | detect stacks among open PRs; indented stacks in the PR list; stack strip in Overview with jump keys | ≈ M3 |
| **12b — Create stacked PRs** | `n` suggests the nearest ancestor branch that has an open PR as base; *New PR on Top* from a PR | small |
| **12c — Restack** | rebase the whole stack onto its new base in one go (one undo step), conflicts through the normal resolver, push all branches, retarget PR bases | ≈ M5 |
| **12d — Merge the stack** | merge bottom-up, restacking between merges, one confirmation | ≈ M4 |

### 12a — See the stack
- **Detection.** A PR is stacked on another when its `baseRefName` equals that PR's `headRefName` and both are open, same-repo PRs. Forks can't be parents: a PR's base must be a branch of the base repository, so cross-repo PRs only ever sit at the top of a stack. Detection runs over *all* open PRs (a cheap list, see Backend) — a stack in "Mine" may have a parent by someone else.
- **PR list.** With `[prs] stack_view` on and no column sort active (ListTable's "original order"), the view orders items depth-first so each stack is contiguous: root first, children indented in the Title cell (`  └ `, two cells per level) with a dim `2/3` position. Sorting by a column (`>` / header click) shows the plain flat list; `>` past the last column returns to stack order.
- **Filtering keeps ancestors.** A small, generic ListTable addition: `context: Callable[[list[T]], list[T]] | None` runs after filtering and may add items back; the PR view uses it to add the ancestors of every match (dimmed), so a filtered child still shows where it sits.
- **Overview strip.** Above the description: `Stack  main ← #12 ✓ Approved ← #13 ● (this) ← #14 ✗ Changes`, each PR in its CI/review colour. `[` / `]` jump to the PR below / above (selecting it in the list, loading it if it's outside the current query).
- **Commits / Files** need no change: they already diff against `merge-base(base, head)`, and the base is the parent's branch, so each PR shows only its own layer.

### 12b — Create stacked PRs
- `n` (create from the current branch): candidates are open-PR head branches `H ≠ B` with `merge-base --is-ancestor H B`; the nearest is the one with the fewest commits in `H..B`. It becomes the default base in the form; the base field offers `[nearest, other candidates…, default branch]`.
- **New PR on Top** (`N`, on a PR): prompts for a branch name, creates it from the PR's head (`refs/gitpanel/pr/<n>` or the local branch), checks it out (Smart / Force Checkout as for `enter`), and records the parent. The PR itself is created later with `n` once there are commits — `gh` refuses empty PRs.
- Every create and restack records the layer in the shared stack file (`<common-dir>/gitpanel/stacks.json`, rule 10): `branch → {parent: branch, parent_head: sha}`. 12c uses it.

### 12c — Restack
**When:** a lower PR merged, or a lower branch got new commits (review fixes), so the layers above no longer sit on top of it. The PR window marks such stacks `⟲ needs restack` (a parent's head isn't an ancestor of its child, or the root's parent is merged).

**What it does,** for the stack containing the selected PR, in one `journal.mutation("Restack #12–#14")`:
1. Fetch the stack's branches and the base (one `git fetch`).
2. Build one todo, bottom layer to top: for each layer, `pick` its own commits, then `update-ref refs/heads/<layer branch>`. A layer's own commits are `<old parent head>..<layer head>`.
3. Check out the top branch and run `scripted_rebase.run(session, new_base, todo)` (rule 7: history rewrites go through scripted rebase; `update-ref` is already a supported todo action). Git moves every intermediate branch when the rebase finishes.
4. Conflicts stop as usual (`RebaseResult("conflict")`): the banner shows *Rebase in progress (3/7)*, the resolver opens, `resume()` finishes — the staged todo survives restarts, so the `update-ref`s still happen.
5. Push all layers: confirm with the list of branches and their old → new heads, then one `git push --atomic --force-with-lease=<b>:<expected>` per remote (expected = the remote-tracking sha before the restack, so someone else's push makes it fail rather than be overwritten).
6. Retarget bases GitHub didn't: GitHub retargets children automatically only when the merged parent's branch is deleted; otherwise `gh pr edit <n> --base <new base>`.

**Squash-merged parents.** A squash merge puts *one new commit* on `main`; its patch-id matches none of the parent's commits, so `--cherry-pick` / patch-id detection can't tell which commits of the child are already in. The reliable boundary is the parent's **final head sha**: the child's own commits are exactly `<parent head>..<child head>`, whatever happened to the parent. Source of that sha, in order: the stack file's `parent_head`; the merged PR's `headRefOid` (`gh pr view <n> --json headRefOid` works after merging and branch deletion); `refs/gitpanel/pr/<n>`. Only when none exist (stack never seen by gitpanel and parent deleted) fall back to `git log --cherry-pick --right-only <new base>...<child>`, and say so in the confirmation.

**Refusals:** a stack branch checked out in another worktree (git won't move it; offer to switch there or skip that layer — skipping stops the restack at that layer); an operation in progress; local branches behind their remote (offer to fast-forward first).

**Undo** restores every branch of the stack (one journal entry; the journal already refuses when a moved ref is checked out elsewhere). Pushes and base retargeting are remote and not undone — the confirmation says so.

### 12d — Merge the stack
`Merge Stack…` on any PR merges it and everything below it, bottom-up: merge the bottom PR (method from `[prs] merge_method`, branch deleted so GitHub retargets), restack the rest onto the base, push, wait for GitHub to report the next PR mergeable, repeat. One confirmation lists every step. Stops at the first failure (failing required checks, conflicts, review required) with the stack left consistent — the remaining PRs restacked and pushed — and a notification saying where it stopped. With `auto`, it enables auto-merge on the bottom PR only and continues when the window next refreshes.

## Backend
| Module | Contents |
|---|---|
| `forge/models.py` | `StackNode(pr: PullRequest, parent: int \| None, children: tuple[int, ...], depth: int)`; `Stack(root_base: str, nodes: tuple[StackNode, ...])` with `order()` (depth-first), `above(n)`, `below(n)`, `position(n) -> (i, total)`, `needs_restack` |
| `forge/github.py` | `stack_index() -> list[PullRequest]` — `gh pr list --state open --limit 300 --json number,headRefName,baseRefName,headRefOid,isCrossRepository` (cheap fields, cached like lists); `stacks(prs) -> list[Stack]` (pure); `retarget(n, base)` — `gh pr edit <n> --base <base>`; `merged_head(n) -> str` — `gh pr view <n> --json headRefOid,state` |
| `git/stack.py` (new, no forge import) | `Layer(branch: str, base_sha: str, head_sha: str)`; `StackRecord` load/save of `stacks.json`; `nearest_base(git, branch, candidates: Sequence[str]) -> str \| None`; `restack_todo(git, layers: Sequence[Layer]) -> list[TodoItem]`; `async def restack(session, new_base: str, layers: Sequence[Layer]) -> RebaseResult` (checks out the top branch, calls `scripted_rebase.run`); `own_commits_fallback(git, new_base, branch)` (cherry-pick fallback) |
| `git/remote.py` | `push_many(git, remote, branches: Sequence[str], leases: Mapping[str, str], *, atomic: bool = True) -> GitResult` |
| `actions/builtin/prs.py` | the actions below; the restack action maps PRs → `Layer`s (forge data + stack file) and calls `git/stack.py` |

`git/stack.py` takes plain branch names and shas, so the git layer stays free of `forge` (rule 1); the action joins the two.

## UI and actions (screen `prs`)
| id | key | phase | notes |

| `pr.create` | `n` | b | (existing) default base = nearest stacked ancestor |

Free keys checked against M11: `enter w o y n r m M c R x` are taken in the PR window, `<` `>` sort, `/` filter. Hints: `[ ] stack` when the selected PR is in a stack, `S restack` when it needs one.

## Config
```toml
[prs]
stack_view = true          # group stacks in the PR list (off: plain list)
restack_push = "ask"       # ask | always | never — push the branches after a restack
```

## Testing
- **Fake gh:** `pr list` with `baseRefName` (already passed through), `pr edit <n> --base <b>` (updates state), `pr view` of merged PRs (keeps `headRefOid`), merging with `--delete-branch` retargets children like GitHub does.
- **Backend (real git):** stack detection (incl. a cross-repo PR that can't be a parent); `nearest_base`; a 3-layer stack after a **squash merge** of the bottom — each branch ends up with only its own commits on the new `main`; after **new commits on a middle layer**; a **conflict mid-stack** → `conflict`, resolve, `resume()` → all three branches moved; **undo** restores all three refs in one step; `push_many` lease rejection when the remote moved.
- **Actions (FakeUi):** restack confirm text, refusal for a layer checked out in another worktree, retarget call when the parent branch wasn't deleted, merge-stack stops at a failing PR.
- **Pilot:** indented stack rows, filter keeps ancestors, `[` / `]` move the selection, `⟲ needs restack` marker.

## Out of scope (for now)
- Other stacking tools — Graphite, ghstack, spr, git-town, jj. gitpanel reads plain GitHub PRs and git branches; their metadata isn't read or written, though their PRs show up as ordinary stacks when bases chain.
- Stacks of local branches without PRs, reordering layers, splitting / folding layers (possible later via the interactive rebase editor over the stack todo).
- GitHub merge queue integration.
